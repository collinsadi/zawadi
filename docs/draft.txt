Hackathon Solutions Architecture



Hackathon Solutions is a solidity contract that will allow seamless distribution of funds post hacakthon, the smart contract allows hackathons organisers to create an hackathon, when they create the hackathon, the hackathon details are sent to  IPFS and then the the CID is sent Onchain to the Hackathon escrow, the hackathon factory has a function  that allows for creation of hackathons the function takes in the IPFS CID and then onchain a keccak256() bytes32 Identifier is created for the hackathon by combining, the msg.sender, who in this case would be considered as the organiser for the hackathon, so the hackathon struct is created, the hackathon struct is made of the hackathon IPFS cid which is a string, and then the organiser address(which is the person who created the hackathon) and the generated unique identifier. After an hackathon escrow is successfully deployed an Event will be emitted, and then the frontend listens to this event and logs the data off chain so as to display to the organiser anytime they come to the platform for better user experience, the hackathon factory keeps track of an array of hackathons structs, it also keeps track of the factory owner, who is the person who has deployed the factory contract, who in this case is probably the contractor, the factory contract has functions to getHackathons by ID, update the address of the organiser of the hackathon (only the organiser or factory owner can do this), transfer ownership of the factory to another address, a function to get all the hackathons, modifiers, events, and custom errors. 

The main Hackathon Escrow contract that will be deployed by the hackathon factory contract:

This contract takes the organiser address as a constructor argument, the organiser address is stored globally, this contract allows for sponsors to add a challenge, just so the hackathon escrow is not spammed with random tokens by random users, the organiser will whitelist addresses of organisers, so there will be a function to whitelist organisers addresses, these white listed address will be able to do what organisers can do, not in any order but a check will just be made if they are whitelisted or not, any whitelisted sponsor can add a challenge to the contract,  the challenge struct, keeps track of totalPrize which is the total pool that will be distributed to the winners, address of the sponsor, a boolean of the challenge have been settled or not (isPaidOut), address of the token (if the price is an ERC20), and a bool to for if the price is an ERC20 or a native token (isERC20), an IPFS cid for details of the sponsor, a bool if the challenge have been funded the amount. The function to  add challenge takes in totalPrice, address of the sponsor is determined by (msg.sender) and must be whitelisted by the organiser, the token address, if the token address is an address zero it is determined that the payment will be done by by native tokens. When the challenge is added successfully, an event is emitted and then that data is also stored off chain, on the contract there is a global challenge tracker it’s a unit256 that get’s increased to get challenge IDs. The contract will have a function for the sponsor to fund the challenge, so when the function to fund/deposit to the challenge is called, the contract checks if the challenge id passed is valid, if it is, then the contract checks if it is expecting ETH or ERC20 token , if it is expecting ETH is get’s the amount from the value, it has to equal the amount specified as total prize, else the contract will revert, if it is expecting an ERC20 the token address is gotten from the struct and used to handle the token transfers using safe ERC20, (all functions in the contract are nonreentrant), the contract first checks if there is enough allowance from the sponsor to spend the totalPrize, if yes, it doesn’t the transfer to the contract and set it as funded. The contract can be locked by the organiser, when the contract is locked and event is emitted, (all actions on the contract emits events with the necessary parameters). The contract has a function to add winners for a challenge, and this is going to be done only by the organiser, the function takes in the challengeId, and an array of address of winners (the winners will be added to the array according to the positions, so if there are 3 address is in the array it means that the first person in the array is the first position), the contract also takes an array called allocation(this is an array of how much should be give to the winners, so the first number in this array should be how much the first address in the winners array should receive, so if there are 3 items in the array of winners there should be 3 uint256 items in the allocations array, and these numbers put together must not be more Than the total price for the challenge), (NB: I think when a challenge is being created it should take the pinata CID of the challenge details, so the frontend can display, I also want to build the system in a way that anyone can build their frontend/backend and just integrate it). When of winners are added an Allocation struct is created, the struct keps track of the position of the winner in the array as a unit256, how much the winner should get (unint256), address of the winner, if the winner has claimed the price(bool). The contract will have a function for a winner to claim their win if they have not already claimed and the total approvals before claim for the challenge have been met (this is going to be a security intensive contract), when the user interacts with the function the user is found in the mapping of allocations that maps the user’s address to their allocation, and then when the token have been transferred to them it is marked as paid out, and then the contract checks if everyone has claimed their funds, if so the contract markes the challenge as marked (NB:  I can’t remember if we are keeping track of if the total funds have been paid out, but we should). The contract is an escrow meaning that before winners can claim their funds the sponsor and the organiser have to approve the withdrawal (this is so the organisers can do any KYC with the winners if they need to do that off chain), so the contract will have a function to approve funds distribution, so when a challenge is being created an approval struct is being created, the approval struct will have 2 fields, sponsorApproved(bool), organiser approved(boolean), and then a mapping of the challenge ID to the approval is made and this is how the checks will be done, when the user wants to claim their funds the challenge is is gotten from the allocation and checked if both sponsor and organiser have approved before the user can claim there tokens or ETH, so when the function to approve the funds the distribution is interacted with, it takes the challenge ID as a parameter, the contract checks if the challenge ID is valid, and then the approval struct for that particular challenge is gotten, so the function checks if the msg.sender is an organiser or sponsor, if any of them have approved and they are interacting with the contract again it should revert, else it is marked as approved for either of them, if the address it neither the sponsor or the organiser the function should revert too.  Sponsors can modify challenges but every checks remain the same
